# بازبینی مستقل کامل‌بودن ذخیره و خواندن از `CodeVia/`

**تاریخ:** ۲۰۲۶-۰۹-۰۷ · **دامنه:** خواستهٔ «اطلاعات پروژه در مخزن باشد، همیشه از آن خوانده شود و فقط اطلاعات مفقود ساخته شود».

## پاسخ صریح

**نه؛ پیاده‌سازی هنوز کامل نیست.** بخش‌های مهمی اجرا و تست شده‌اند، ولی تأیید قبلی مبنی بر کامل بودن، بیش از حد کلی بود. صرف داشتن فایل در Git یا سبز بودن regression، اثبات نمی‌کند آن اطلاعات واقعاً در همهٔ مسیرهای استفاده مصرف می‌شوند.

در این بررسی **۸ نقص قابل بازتولید** پیدا شد. کد اجرایی محصول در نوبت ممیزی تغییر نکرد؛ این موارد **هنوز رفع نشده‌اند**.

### نتیجهٔ اجرا

| بررسی | نتیجه |
|---|---|
| کل regression | **۵۴۷ تست، ۴۰ فایل: موفق** |
| تست متمرکز repository state | **۵۴ تست: موفق** |
| Smoke | **۳۳/۳۳: موفق** |
| Typecheck و build | **موفق** |
| بررسی‌های مستقل این گزارش | **۸ شکاف، ۳ کنترل موفق، صفر خطای probe** |

این اعداد با هم تناقض ندارند: سناریوهای زیر در تست‌های قبلی پوشش کافی نداشتند. شمارش شکاف‌ها، درصد کامل‌بودن محصول نیست.

## روش بررسی و حدود شواهد

- بازخوانی loader، codecها، coordinator، context سازندهٔ پرامپت، APIهای ویرایش/حذف، حافظه، تاریخچه و مسیر migration.
- اجرای `scripts/audit-repository-state.mjs` روی دیتابیس‌های موقت و **Mock GitHub / مدل ساختگی**؛ `fetch` خروجی صریحاً ممنوع است.
- در R01 درخواست واقعیِ ارسال‌شده به adapter مدل Mock ضبط شد. یک قانون مثبت به مدل رسید، اما متن ویژهٔ فایل context نرسید؛ بنابراین نتیجه ناشی از ضبط‌نشدن درخواست مدل نبود.
- سناریوهای migration، fixture یک نصب قدیمی‌اند؛ ادعای اجرای migration روی دادهٔ واقعی کاربر نیستند.
- هیچ مخزن خارجی، کلید واقعی، سرویس پولی یا ارسال تلگرام واقعی درگیر نبود.
- رفتار سرویس‌های واقعی، کنترل دسترسی و تمامی آسیب‌پذیری‌های [ممیزی عمومی قبلی](PIPELINE_AUDIT.md) در این بررسی دوباره آزموده نشده‌اند.

بازتولید:

```bash
node --import tsx scripts/audit-repository-state.mjs
```

خروجی ساختاریافته: `data/audit/repository-state-audit.json` (عمداً Git-ignored).

Exit code `1` یعنی قرارداد برآورده نشده؛ `2` یعنی خود probe مشکل دارد. در اجرای نهایی: `1`، بدون خطای probe.

## چه بخش‌هایی واقعاً کار می‌کنند؟

- **P01 — استفادهٔ مجدد:** دومین onboarding روی پوشهٔ کامل، **صفر commit و صفر فراخوانی مولد تعریف** داشت.
- **P02 — کشف اسکیل از Git:** فایل مهارت جدید بدون seed کردن DB، از API کاتالوگ پروژه با متن کامل و namespace همان پروژه خوانده شد.
- **P03 — حافظهٔ کامل:** سند **۷۵۲۰ کاراکتری** شامل فارسی، تیتر تو‌در‌تو و ارجاع، پس از پاک کردن ایندکس دقیقاً بازیابی شد.
- تست‌های فعلی همچنین ویرایش معمول ایجنت، حفظ وضعیت غیرفعال در پوشهٔ استاندارد، تاریخچهٔ پرامپت و diff/restore، وابستگی‌های مهارت فعال، محدودیت AI، timeout، بازسازی به DB خالی و تعارض ویرایش شناخته‌شده را پوشش می‌دهند.

این‌ها تأیید مسیرهای مشخص‌اند، نه تضمین همهٔ حالت‌های ممکن.

## نقص‌های باز

### R01 — context ذخیره می‌شود، اما متن آن در مسیر پیش‌فرض به مدل نمی‌رسد — زیاد

**شاهد:** یک قید یکتا فقط در `CodeVia/context.md` قرار گرفت. فایل در Git موجود بود؛ اجرای research موفق و یک فراخوانی مدل ضبط شد. قانون کنترل مثبت به مدل رسید، ولی قید context نه در درخواست مدل بود و نه در `renderPromptContext` پیاده‌سازی.

**علت:** `ContextEngine.build` منبعی برای متن این سند ندارد. `buildContextPack` مسیرهای `CodeVia/` را از درخت محتوایی کنار می‌گذارد و از context فقط رجیستری را استخراج می‌کند.

**محل:** `src/ai/context-engine.ts:44–85`، `src/agents/context.ts:124–127,273`.

**اثر:** حفظ یادداشت معماری در Git لزوماً به معنی رعایت آن توسط ایجنت نیست. خواندن صریح فایل می‌تواند آن را وارد کند؛ مشکل، مصرف خودکار در مسیر پیش‌فرض است.

**اصلاح لازم:** افزودن منبع صریح و محدودشدهٔ متن canonical context به context مدل و تستِ رسیدن متن به درخواست نهایی؛ نه فقط تستِ باقی ماندن فایل.

### R02 — متن سابقهٔ تسک/اجرای پایان‌یافته هنوز می‌تواند از DB خوانده شود — زیاد

**شاهد:** پس از اتمام موفق یک تسک، عنوان و توضیح تسک و خلاصهٔ run فقط در Git ویرایش شدند. GET هر دو منبع `200` بود، ولی هیچ‌یک از متن‌های جدید را نشان نداد.

**علت:** restore برای **هر** تسک یا run موجود در DB، نه فقط اجرای زنده، نوشتن از Git را رد می‌کند.

**محل:** `src/github/project-state.ts:507,517`.

**اثر:** قرارداد «همیشه از مخزن بخوان» برای تاریخچه کامل نیست؛ اصلاح توضیح یک تسک در Git می‌تواند در استفادهٔ بعدی دیده نشود.

**اصلاح لازم:** تفکیک دقیق فیلدهای runtime/لغو از محتوا و سابقهٔ پایان‌یافته. رفع این مورد نباید تسک لغوشده را دوباره فعال کند.

### R03 — workflow حذف‌شده با کپی مخزن دوباره ساخته می‌شود — زیاد

**شاهد:** `bug-diagnosis-loop` از API حذف شد و tombstone در Git ماند. onboarding در همان پروژه حذف را رعایت کرد، اما کپی پوشه به پروژهٔ جدید workflow را با شناسهٔ تازه ساخت؛ tombstone قبلی هم همچنان وجود داشت.

**علت:** تشخیص غیبت، مسیر مشتق از شناسهٔ **پروژهٔ جدید** را بررسی می‌کند؛ حذف ثبت‌شده زیر شناسهٔ قبلی را به هویت منطقی workflow وصل نمی‌کند.

**محل:** `src/agents/project-state.ts:87` و تولید شناسه در `workflowDrafts`.

**اصلاح لازم:** tombstone باید هویت منطقی/slug و namespace قابل بازبستن داشته باشد، نه اینکه فقط از وجود یک filename نتیجه گرفته شود.

### R04 — حذف ایجنت پس از جابه‌جایی فایل، پایدار نیست — زیاد

**شاهد:** فایل research به `CodeVia/agents/custom-research-location.md` منتقل شد؛ loader این مسیر را شناخت. پس از حذف همان ایجنت از API و اجرای onboarding، research تازه در `CodeVia/agents/research.md` ساخته شد.

**علت:** بررسی حذف/غیبت ایجنت پیش‌فرض به مسیر مبتنی بر type تکیه دارد؛ tombstone مسیر واقعیِ تغییرنام‌یافته کافی نیست.

**محل:** `src/agents/project-state.ts:62`، حذف در `src/http/routes/agents.ts`.

**اصلاح لازم:** ثبت و خواندن هویت حذف‌شده مستقل از نام فایل، همراه با تست rename → delete → reuse.

### R05 — مهاجرت یک ایجنت قدیمیِ فقط-DB تعریف آن را از استفادهٔ فعال خارج می‌کند — زیاد

**شاهد:** fixture قدیمی یک research با پرامپت سفارشی، `enabled:false`، مجوزهای خالی و بودجهٔ **۳۲۱** داشت، اما فایل تعریف در Git نداشت. پس از onboarding اول research در roster نبود. onboarding دوم آن را با شناسهٔ جدید، **فعال**، مجوزهای پیش‌فرض و بودجهٔ **۲۰۰۰۰** ساخت؛ پرامپت سفارشی استفاده نشد.

یک نسخهٔ متن در آرشیو پرامپت ماند؛ بنابراین ادعای پاک‌شدن تمام ردپاها درست نیست. اما تعریف کامل، محدودیت و غیرفعال بودنِ ایجنت قبلی حفظ و استفاده نشد.

**علت:** هنگام bootstrap وجود رکورد DB باعث می‌شود ایجنت از لیست «باید فایلش ساخته شود» حذف شود؛ پس از نوشته شدن manifest، restore آن رکورد فاقد فایل را پاک می‌کند.

**محل:** `src/agents/project-state.ts:59–63`، `src/github/project-state.ts:466`.

**اصلاح لازم:** migration صریحِ تعریف کاملِ legacy پیش از پاک‌سازی ایندکس؛ با حفظ شناسه، وضعیت و حدود قبلی و بدون فعال‌سازی دوباره.

### R06 — migration گردش‌کارهای قدیمی ناقص است — زیاد

**شاهد:** یک workflow سفارشی غیرفعال هم در DB و هم در `.ai-engineering/workflows/` بود. پس از migration فقط دو workflow پیش‌فرض جدید در ایندکس بودند. فایل legacy حذف نشد، ولی workflow سفارشی خوانده/منتقل نشد.

**علت:** coordinator فقط `snapshot.workflows` زیر مسیر جدید را مبنا می‌گیرد؛ migration فعلی حافظه و تاریخچهٔ پرامپت، معادل migration همهٔ اجزا نیست.

**محل:** `src/agents/project-state.ts:86–87`، `src/github/project-state.ts:499–501`.

**اصلاح لازم:** import نسخه‌دار و اعتبارسنجی‌شدهٔ workflowهای قدیمی و رکوردهای معتبرِ فقط-DB قبل از تولید پیش‌فرض یا حذف cache.

### R07 — شکست ذخیرهٔ لغو کار، بدون همگام‌سازی مجدد باقی می‌ماند — متوسط

**شاهد:** با خطای موقت نوشتن Git، cancel پاسخ `200` داد و DB لغوشده بود. پس از برگشت Git، cancel دوباره هم `200 / alreadyFinal` داد، ولی فایل مخزن هنوز `created` بود؛ علامت صریح unsynced هم برنگشت.

**توضیح:** لغو محلی باید هنگام قطعی Git کار کند. نقص، متوقف نکردن کار نیست؛ نبود retry/اعلام وضعیت همگام‌نشده است. یک sync صریح بعدی یا تکمیل اجرای دیگری ممکن است آن را بنویسد، اما مسیر cancel این را تضمین نمی‌کند.

**محل:** `src/agents/manager.ts:311–321`، `src/http/routes/tasks-runs.ts:94–102`.

**اصلاح لازم:** ثبت پایدار pending sync، retry پس از بازگشت اتصال و نمایش جدای وضعیت اجرا از وضعیت ذخیره در Git.

### R08 — برخی فیلدهای عددی خراب با پیش‌فرض جایگزین می‌شوند — زیاد

**شاهد:** در فایل ایجنت schema 2، `tokenBudget`، `maxIterations` و `version` رشتهٔ نامعتبر و `timeoutMs` مقدار null گرفتند. خواندن رد نشد؛ مقادیر به‌ترتیب **۲۰۰۰۰، ۵، ۱ و ۱۲۰۰۰۰** شدند.

**علت:** helper عددی قبل از اعتبارسنجی، ورودی نامعتبر را با fallback جایگزین می‌کند. اعتبارسنجی بعدی دیگر ورودی خراب اصلی را نمی‌بیند.

**محل:** `src/github/project-codec.ts:51,272–286`، فراخوانی parser در `src/github/project-state.ts`.

**اصلاح لازم:** schema 2 باید روی دادهٔ خام سخت‌گیرانه بررسی شود. defaultهای سازگاری با نسخهٔ legacy نباید محدودیت خراب یک تعریف جدید را افزایش دهند.

## تفاوت «همهٔ اطلاعات» با دامنهٔ واقعی

- داده‌های اصلی پروژه به فایل‌های تعریف‌شده محدودند. فایل Markdown دلخواه صرفاً با قرار گرفتن زیر `CodeVia/` خودکار به دانش مدل تبدیل نمی‌شود؛ R01 نمونهٔ مشخص‌تر همین فاصله است.
- AI متن پرامپت، دستورالعمل مهارت، قوانین و شرح workflow را می‌نویسد؛ roster و گراف‌های اولیه عمدتاً از الگوهای کد می‌آیند. «همه چیز آزادانه توسط AI طراحی می‌شود» پیاده نشده و اعطای آزاد مجوز توسط AI هم مطلوب نیست.
- آمار تجمیعی run در Git هست، ولی دفتر کامل cost، audit و notificationها، تنظیم provider/modelهای سراسری و حساب‌ها کاملاً از این پوشه بازسازی نمی‌شوند.
- API key، credential، نشست و lease صف عمداً باید بیرون Git بمانند. رفع نواقص بالا نباید با dump کردن کل DB یا اسرار به مخزن انجام شود.
- اتصال واقعی GitHub/model، کیفیت خروجی AI، شاخه‌های محافظت‌شده و مقیاس بالا هنوز نیازمند آزمون عملی جداگانه‌اند.

## ترتیب پیشنهادی رفع

1. **R05 و R06:** جلوگیری از آسیب migration؛ پیش از upgrade/onboard روی دادهٔ قدیمی backup بگیرید.
2. **R03 و R04:** حذف پایدار با هویت مستقل از مسیر/شناسهٔ پروژه.
3. **R08:** رد تنظیم خراب قبل از defaultگذاری یا هر اثر اجرایی.
4. **R01 و R02:** یکی شدن ذخیره‌سازی با مصرف واقعی اطلاعات.
5. **R07:** outbox/retry و اعلام وضعیت ذخیره‌سازی.

پس از اصلاح، همین probeها باید از `gap` به `pass` تبدیل و به regression مطلوب اضافه شوند. **در این نوبت فقط بررسی و گزارش انجام شده است، نه رفع این هشت نقص.**

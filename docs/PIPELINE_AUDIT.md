## پاسخ صریح در زمان ممیزی

**نه؛ همهٔ اجزا کامل نیستند و وضعیت فعلی برای استقرار عمومی یا چندکاربرهٔ حساس آماده نیست.**

مسیر اصلی «درخواست → brief پژوهشی → برنامهٔ JSON → تسک‌های تخصصی → تخصیص اسکیل → اجرای ایجنت» پیاده‌سازی شده است. اما حفظ تنظیمات، رفع ابهام، تحویل کامل زمینه، ارزیابی مستقل QA، بازیابی و کنترل دسترسی هنوز نقص دارند. سبز بودن تست‌های قبلی، کامل بودن این قراردادها را اثبات نمی‌کرد.

در نوبت ممیزی **کد اجرایی محصول اصلاح نشده بود**؛ ابزار ممیزی و این گزارش اضافه شده‌اند و ادعاهای بیش‌ازحد در مستندات تعدیل شده‌اند. تمام موارد A01 تا A18 زیر در زمان ممیزی باز بودند. این گزارش لزوماً منشأ هر نقص را به تغییرات نوبت قبل نسبت نمی‌دهد؛ موضوع آن وضعیت فعلی کل مسیر و وابستگی‌های آن است.

- بازخوانی مسیرهای Autonomous، تک‌ایجنت و Workflow، تنظیمات و مدل‌ها، انتخاب اسکیل، persistence، صف/worker، auth/RBAC، realtime، approvals و ابزارهای GitHub.
- اجرای **۱۸ سناریوی تشخیصی مستقل و هدفمند** در `scripts/audit-pipeline.mjs`: در اجرای نهایی **۱۸ شکاف، صفر خطای ابزار ممیزی** ثبت شد. این‌ها سناریوهای انتخاب‌شده برای بررسی خلأهای مشکوک‌اند؛ نه نمونهٔ آماری از کل محصول و نه درصد پیشرفت پروژه.
- وضعیت برنامه در دیتابیس‌های موقت SQLite؛ GitHub از نوع Mock و پاسخ مدل‌ها ساختگی است. `fetch` خروجی در اسکریپت ممنوع است. بررسی Socket.io از یک اتصال واقعی ولی موقت و محلی استفاده می‌کند. هیچ درخواست مدل پولی، ارسال تلگرام واقعی، merge یا تغییر مخزن خارجی انجام نشد.
- A07 ابتدا در حالت انتخاب جدیدترین مدل موفق بود. با کنترل مثبت برای همان حالت و بررسی انتخاب یک مدل قدیمی‌تر، نقص وابسته به ترتیب کاتالوگ آشکار شد؛ موفقیت حالت اول به‌تنهایی برای رد فرضیه کافی نبود.

## شکاف‌های بازتولیدشده

شدت‌های زیر اولویت مهندسی این ممیزی‌اند، نه امتیاز رسمی CVSS. **P0** یعنی مانع انتشار عمومی؛ **P1** یعنی نقص مهم قرارداد اجرایی یا سلامت داده.

### A01 — P0 / بحرانی: دور زدن strict authentication

- **سناریو:** strict auth و تنظیمات آزمایشی OAuth فعال؛ درخواست بدون session به `/admin/settings`.
- **مشاهده:** بدون هدر `401`؛ با هدر هویت دلخواه `200`، بدون ورود معتبر.
- **ریشه:** `src/http/auth.ts:56–58` هدر `x-user-id` را به هویت با نقش demo-owner تبدیل می‌کند؛ شرط `src/http/auth.ts:84` همان هدر را از الزام ورود مستثنا می‌کند.
- **اصلاح لازم:** override تستی باید صریحاً به محیط/سازوکار امن تست محدود شود؛ هدر ارسالی مشتری هرگز مدرک هویت نباشد. strict mode در محیط واقعی باید fail-closed باشد.

### A02 — P0 / بحرانی: نبود کنترل مالکیت و RBAC مؤثر در مسیرهای پروژه

- **سناریو:** کاربر دوم با session معتبر و نقش viewer؛ پروژه متعلق به کاربر اول.
- **مشاهده:** پروژه در فهرست مخفی است، اما GET مستقیم و PATCH هر دو `200` و شرح پروژه واقعاً تغییر می‌کند.
- **ریشه:** فیلتر فهرست در `src/http/routes/projects.ts:51–56`؛ GET/PATCH بدون بررسی مالک در `:124–176`؛ middleware سراسری در `src/http/app.ts:291` بدون `can` فراخوانی می‌شود.
- **اصلاح لازم:** کنترل دسترسی یکپارچه برای هر منبع، تطبیق پروژهٔ task/run/agent با کاربر، و permission واقعی عملیات نوشتن. مخفی‌کردن UI یا فهرست کافی نیست.
- **مرز اثبات:** GET/PATCH پروژه بازتولید شد؛ تک‌تک endpointهای دیگر با سناریوی مستقل آزمایش نشده‌اند.

### A03 — P0 / بحرانی: دریافت realtime پروژه توسط اتصال ناشناس

- **سناریو:** اتصال واقعی Socket.io بدون cookie/token، با strict auth فعال؛ انتشار یک رویداد پروژه با نشانگر خصوصی آزمایشی.
- **مشاهده:** اتصال برقرار شد و نشانگر پروژه دریافت شد.
- **ریشه:** `src/http/app.ts:108–122` فاقد middleware احراز هویت socket و room مجاز پروژه است؛ `io.emit` همهٔ رویدادها را broadcast می‌کند.
- **اصلاح لازم:** احراز هویت handshake، عضویت مجاز در room پروژه و انتشار محدود رویدادها. محدودکردن CORS به‌تنهایی جای authorization نیست.

### A04 — P1 / بالا: worker مرج، اعتبار approval را بررسی نمی‌کند

- **سناریو:** قرار دادن job داخلی `github.op/merge_pr` با شناسهٔ approval ناموجود در صف موقت.
- **مشاهده:** adapter مرج یک بار فراخوانی شد و job موفق اعلام شد؛ هیچ رکورد approval وجود نداشت.
- **ریشه:** `src/workers/worker.ts:159–164` فقط وجود یک مقدار `approvalId` را می‌سنجد؛ وضعیت approved، پروژه، عملیات، PR و commit تطبیق داده نمی‌شوند. مسیر از GitHub adapter عمومی worker نیز استفاده می‌کند.
- **اصلاح لازم:** اعتبارسنجی رکورد و موضوع دقیق تأیید، جلوگیری از استفادهٔ مجدد نامجاز و استفاده از اتصال مجاز همان پروژه.
- **مرز اثبات:** این آزمون مستقیماً job داخلی تولید کرده است؛ مسیر سوءاستفادهٔ HTTP عمومی برای enqueue این نوع job اثبات نشده و مرج واقعی انجام نشده است.

### A05 — P1 / بالا: regeneration تنظیمات دستی عامل را از بین می‌برد

- **سناریو:** تنظیم دستی عامل Backend و محدودیت‌ها، سپس ویرایش capabilities از API با re-onboarding خودکار.
- **مشاهده:** **۹ فیلد** بازنویسی شدند: `systemPrompt`، `projectPrompt`، `models`، `tools`، `permissions`، `maxIterations`، `timeoutMs`، `tokenBudget` و `enabled`. مجوز نوشتن حذف‌شده دوباره اضافه شد.
- **ریشه:** `src/agents/generator.ts:224–244` بیشتر عامل را از scaffold می‌سازد؛ `src/http/routes/projects.ts:185–190` تغییر capabilities را به آن متصل می‌کند.
- **اصلاح لازم:** تفکیک مقادیر تولیدشده و overrideهای دستی برای همهٔ فیلدها، نه فقط skills؛ محدودیت‌های کاربر نباید بدون تأیید باز شوند.

### A06 — P1 / بالا: عامل دستی ذخیره می‌شود ولی در roster پروژه نیست

- **سناریو:** `POST /agents` برای ساخت عامل جدید.
- **مشاهده:** پاسخ `201` و جست‌وجوی مستقیم با id موفق؛ عامل در `byProject` دیده نمی‌شود و lookup نوع آن را انتخاب نمی‌کند.
- **ریشه:** `src/agents/agent-repo.ts:12–24` در create، metadata مربوط به `projectId` را به upsert نمی‌دهد. `src/db/repository.ts:47–53,114–133` این ایندکس را از JSON استنتاج نمی‌کند.
- **اصلاح لازم:** ایندکس درست هنگام ساخت، migration رکوردهای قدیمی بدون ایندکس و قرارداد روشن برای چند عامل هم‌نوع. نقش هم‌نوع بودن به‌تنهایی دلیل انتخاب‌نشدن نیست؛ غیبت از roster مستقلاً ثابت شد.

### A07 — P1 / بالا: مدل پیش‌فرض انتخابی زیر سایهٔ specialization خودکار می‌رود

- **سناریو:** دو مدل فعال و مناسب کدنویسی؛ انتخاب مدل قدیمی‌تر به‌عنوان default، بدون تعیین دستی specialized model.
- **مشاهده:** primary همان مدل انتخابی است، اما `specialized.coding` مدل جدیدترِ انتخاب‌نشده است و router ابتدا آن را برمی‌گزیند. کنترل مثبت انتخاب مدل جدیدتر موفق است.
- **ریشه:** `src/agents/generator.ts:297–313` تخصص‌ها را از اولین مدل مناسب کاتالوگ می‌گیرد؛ `src/ai/model-router.ts:78–90` تخصص را جلوتر از primary قرار می‌دهد.
- **اصلاح لازم:** مقدار تخصصی تولیدشده باید انتخاب معتبر کاربر را حفظ کند؛ specialization صریح کاربر با default تولیدشده اشتباه نشود. سیاست ارث‌بری هنگام تغییر default پروژه هم مشخص شود.

### A08 — P1 / بالا: GitHub تعریف اسکیل سفارشی را بازیابی نمی‌کند

- **سناریو:** ساخت و اتصال اسکیل سفارشی دارای instructions و dependency، sync، حذف تعریف از کاتالوگ محلی، سپس restore.
- **مشاهده:** slug همچنان به پروژه متصل است، اما تعریف اسکیل بازسازی نمی‌شود.
- **ریشه:** `src/github/project-files.ts:199–213` فقط slug و توضیح را ذخیره می‌کند؛ `restore` در `:512–516` حتی repository کاتالوگ اسکیل را دریافت نمی‌کند.
- **اصلاح لازم:** schema نسخه‌دار برای instructions، prerequisites، سازگاری، وضعیت فعال و نسخهٔ اسکیل، همراه اعتبارسنجی و حل تعارض. Git restore فعلی معادل backup کامل DB نیست.

### A09 — P1 / بالا: از دست رفتن محتوای حافظه با تیتر Markdown

- **سناریو:** render/parse حافظه‌ای که در متن خود `## Risks` و `### Details` دارد.
- **مشاهده:** متن **۷۲ کاراکتری به ۷ کاراکتر** تبدیل شد؛ بخش ریسک حذف شد.
- **ریشه:** `src/github/project-files.ts:339–369` تیترهای خود محتوا را separator ساختار فایل فرض می‌کند. restore در `:566–571` می‌تواند متن ناقص را جایگزین حافظهٔ DB کند.
- **اصلاح لازم:** serialization بدون اتلاف برای محتوای چندخطی و مهاجرت سازگار. رفع قبلی Markdown تسک، این parser جداگانهٔ حافظه را پوشش نمی‌داد.

### A10 — P1 / بالا: تداخل حافظهٔ restoreشده میان پروژه‌ها

- **سناریو:** دو پروژهٔ جدا، هرکدام restore یک memory key یکسان.
- **مشاهده:** شمار رکورد موردنظر در دو پروژه **`[0, 1]`** شد، نه `[1, 1]`؛ رکورد اول از پروژهٔ اول ناپدید شد.
- **ریشه:** `src/github/project-files.ts:576` شناسه را فقط از `mem-restored-${key}` با برش ۶۰ کاراکتری می‌سازد؛ شناسه در DB سراسری است.
- **اصلاح لازم:** شناسهٔ پروژه‌محور یا UUID، uniqueness مناسب و migration. خطر برخورد کلیدهای بلند در همان پروژه نیز باید آزمون شود.

### A11 — P1 / بالا: Pull دستی وضعیت runtime را به عقب برمی‌گرداند

- **سناریو:** فایل Git وضعیت قدیمی `created` دارد؛ وضعیت همان تسک در DB اکنون `cancelled` است؛ فراخوانی Pull پروژه.
- **مشاهده:** پاسخ `200` و وضعیت بعد از Pull دوباره `created` شد.
- **ریشه:** `src/http/routes/projects.ts:196–205` restore را بدون `includeTasks:false` فراخوانی می‌کند؛ `src/github/project-files.ts:549–560` وضعیت را بی‌قید از فایل می‌گیرد.
- **اصلاح لازم:** جداسازی restore تنظیمات از restore تاریخچه/اجرا، منع بازنویسی task زنده یا cancelled و بازیابی صریح با conflict policy. حفاظت پیش از اجرای Autonomous از قبل وجود دارد؛ نقص مربوط به Pull دستی است.
- **مرز اثبات:** لغو از API خود برنامه با پاسخ `200` و سپس Pull در محیط fixture انجام شد؛ سناریوی هم‌زمان مرورگر و شبکهٔ کند جداگانه اجرا نشده است.

### A12 — P1 / بالا: job رهاشده در running بازیابی نمی‌شود

- **سناریو:** job قبلاً claim شده و زمان شروع آن قدیمی است؛ بازسازی نمونهٔ JobQueue و تلاش برای claim/retry دستی.
- **مشاهده:** وضعیت `running` باقی می‌ماند، صفر job بازپس‌گیری می‌شود و retry تسک `409` می‌گیرد.
- **ریشه:** `src/db/queue.ts:47–68` فقط pending/retrying را claim می‌کند؛ startup در `src/index.ts:44–47` و worker فاقد lease/reconciliation هستند.
- **اصلاح لازم:** lease/heartbeat یا بازیابی مالک اجرا، reconcile وضعیت task/run/job و کنترل idempotency پیش از تکرار اثر خارجی.
- **مرز اثبات:** بازسازی queue روی همان DB و بازخوانی startup؛ فرآیند سیستم‌عامل عمداً kill نشده است.

### A13 — P1 / بالا: مانع اعلام‌شدهٔ پژوهش جلوی کدنویسی را نمی‌گیرد

- **سناریو:** پاسخ پژوهش صریحاً می‌گوید قرارداد احراز هویت نامعلوم است، از کاربر سؤال کنید و تا پاسخ هیچ فایلی نسازید؛ پاسخ بعدی مدل یک برنامهٔ ساختاری معتبر می‌دهد.
- **مشاهده:** brief حاوی BLOCKER ذخیره شد، یک مرحلهٔ موفق `write_file` اجرا شد و تسک به `succeeded` رسید.
- **ریشه:** `src/agents/planning.ts:6–12` مانع را فقط در متن می‌خواهد؛ `src/agents/orchestrator.ts:228–246` مستقیماً از brief به planning و اجرای مراحل می‌رود.
- **اصلاح لازم:** خروجی پژوهشی ساختاری با وضعیت تصمیم، gate اجرایی، ثبت سؤال، پاسخ کاربر و ادامهٔ همان تسک. دستور «مانع را بنویس» در پرامپت جای state machine نیست.

### A14 — P1 / بالا: dependsOn لزوماً قرارداد producer را به consumer نمی‌رساند

- **سناریو:** بک‌اند `src/services/session-service.ts` می‌سازد؛ فرانت‌اند `public/signin-view.tsx` با وابستگی صریح به همان تسک اجرا می‌شود.
- **مشاهده:** ترتیب اجرا درست و تسک موفق است، اما محتوای یکتای backend در هیچ پیام درخواست مدل frontend وجود ندارد.
- **ریشه:** `src/agents/orchestrator.ts:316–325` handoff صریح را فقط برای مخزن‌های دیگر می‌سازد؛ `src/agents/context.ts:144–154` در یک مخزن به هم‌پوشانی نام entity و فایل‌های هم‌پوشه وابسته است.
- **اصلاح لازم:** artifact/contract manifest بر اساس شناسهٔ dependency و SHA برای هر دو حالت تک‌مخزنی و چندمخزنی، با بودجهٔ context و اعلام صریح حذف/خلاصه‌سازی. صرف نمایش نام فایل کافی نیست.

### A15 — P1 / بالا: QA مستقلِ معیار پذیرش اجرا نمی‌شود

- **سناریو:** برای QA هم مدل پاسخ‌ساختگیِ قابل‌ردیابی تنظیم شده؛ خروجی پیاده‌ساز عمداً با هدف رد ورود نامعتبر سازگار نیست.
- **مشاهده:** **صفر فراخوانی مدل QA و صفر توکن**؛ فقط `read_file`، `run_tests` و `save_memory`. تسک با `verification: simulated` موفق است.
- **ریشه:** `src/agents/orchestrator.ts:359–372` یک plan ثابت می‌دهد؛ `src/agents/runner.ts:121–154` برای این plan، chat مستقلی ایجاد نمی‌کند. بررسی کد نیز evaluator اتصال هر معیار پذیرش به شواهد آزمون را نشان نمی‌دهد.
- **اصلاح لازم:** verdict ساختاری برای هر معیار، شواهد آزمون مرتبط، موارد پوشش‌داده‌نشده و تصمیم failed/needs-review؛ review مدل می‌تواند مکمل باشد، نه جایگزین تست اجرایی.
- **مرز اثبات:** موفقیت Mock به معنای «CI واقعی باگ را پذیرفت» نیست؛ آن مسیر عمداً simulated است. نقص، نبود ارزیابی مستقل در کد و اجراست، نه خودِ برچسب simulated. خواندن CI همان SHA در مسیر واقعی پیاده شده است.

### A16 — P1 / بالا: برنامه‌ریزی چندمخزنی کد موجود مخزن مقصد را نمی‌بیند

- **سناریو:** `audit/config` مخزن تنظیمات و `audit/backend` مخزن پیاده‌سازی است؛ backend از قبل `src/ExistingAuthEntry.ts` دارد.
- **مشاهده:** مسیر فایل موجود در هیچ پیام planning حاضر نیست؛ فقط لینک مخزن‌ها در تعریف پروژه وجود دارد.
- **ریشه:** `src/agents/orchestrator.ts:222,231–232` یک pack می‌سازد؛ `src/agents/context.ts:89–118` آن را از `configRepo` می‌خواند.
- **اصلاح لازم:** جمع‌آوری context محدود ولی مرتبط از همهٔ مخزن‌های متأثر پیش از refinement/planning، با repo/ref دقیق. مشاهدهٔ مخزن مقصد در مرحلهٔ implement جای این پیش‌نیاز را نمی‌گیرد.

### A17 — P1 / بالا: موفقیت ظاهری action اجرا‌نشده در Workflow

- **سناریو:** workflow معتبر با یک node از نوع `telegram` و adapter آزمایشی قابل‌شمارش.
- **مشاهده:** وضعیت `succeeded` و خروجی `{ok:true}`، اما **صفر پیام ارسالی**.
- **ریشه:** `src/workflow/graph.ts:3–13` این نوع را معتبر می‌داند؛ `src/workflow/engine.ts:201–202` برای انواع بدون handler، موفقیت پیش‌فرض برمی‌گرداند.
- **اصلاح لازم:** handler واقعی یا رد صریح unsupported. نود ساختاری مثل trigger/parallel می‌تواند آگاهانه no-op باشد، اما action باید قرارداد اثر قابل‌آزمون داشته باشد. webhook نیز از نظر source نیازمند تعیین همین قرارداد است؛ آزمون مستقل اینجا روی telegram انجام شد.

### A18 — P1 / بالا: timeout ابزار، خود عملیات را متوقف نمی‌کند

- **سناریو:** ابزار صرفاً درون‌حافظه‌ای با timeout پنج میلی‌ثانیه و اثر تأخیری ۳۵ میلی‌ثانیه.
- **مشاهده:** caller خطای timeout دریافت کرد، ولی بعداً اثر ابزار رخ داد.
- **ریشه:** `src/tools/registry.ts:81,104–109` فقط Promise را با timer رقابت می‌دهد؛ AbortSignal یا توقف عملیات زیربنایی ندارد.
- **اصلاح لازم:** لغو cooperative تا adapter، کنترل قبل از commit، و reconciliation/idempotency برای درخواست خارجی درحال‌پرواز. حتی AbortController تضمین بازگشت عملیات پذیرفته‌شدهٔ سمت GitHub نیست.
- **مرز اثبات:** اثر تنها تغییر یک متغیر fixture بود؛ نوشتن دیرهنگام در مخزن واقعی انجام یا ادعا نشده است.

## محدودیت‌های اضافی بر پایهٔ خواندن کد، خارج از شمار ۱۸ سناریو

1. **پژوهش خارجی:** ابزار `search` فقط حافظه و نام مسیرهای repository را جست‌وجو می‌کند (`src/tools/core-tools.ts:173–213`). واکشی وب، ارجاع منابع و ارزیابی تازگی منبع پیاده نشده است. اگر منظور پژوهش صرفاً تحلیل پروژه باشد، این یک مرز دامنه است؛ اگر تحقیق اینترنتی لازم باشد، کار باقی‌مانده است.
2. **حلقهٔ انتخاب ابزار توسط مدل:** اجرا فعلاً تولید deliverable توسط مدل + plan ابزارِ کنترل‌شده است، نه حلقهٔ عمومی model → tool call → observation → replanning (`src/agents/runner.ts:121–162`، `src/agents/plan.ts:26–84`). تعدادی عنوان Research صرفاً مرحلهٔ نمایشی‌اند و ابزار جست‌وجو اجرا نمی‌کنند.
3. **`maxIterations`:** ذخیره و نمایش داده می‌شود، اما در حلقهٔ runner شرطی بر اساس آن وجود ندارد (`src/agents/runner.ts:162`). بودجهٔ token/call/time و سقف fix loop سازوکارهای جداگانه و موجود هستند؛ نبود کنترل iteration به معنی نبود همهٔ محدودیت‌ها نیست.
4. **همهٔ نقش‌ها:** Autonomous هفت نوع نویسنده به‌علاوهٔ Research/QA دارد (`src/agents/implementation.ts:11`). وجود ۱۸ نوع عامل در کاتالوگ، به معنی اجرای تخصصی کامل هر ۱۸ نقش در این حلقه نیست؛ بقیه عمدتاً مسیر مستقیم/Workflow دارند.
5. **کاتالوگ اسکیل با پیش‌نیاز غیرفعال:** `availableSkills` فعال/سازگار بودن root را می‌سنجد، ولی وابستگی‌ها بعداً در `resolveSkillDependencies` بررسی می‌شوند (`src/skills/assignment.ts:33–52,61–77,120`). نتیجه fail-closed است، اما planner می‌تواند گزینه‌ای غیرقابل‌اجرا ببیند. حذف آن از گزینه‌ها یا نمایش علت عدم‌دسترسی باید تعیین تکلیف شود.
6. **restore کامل پروژه:** manifest و restore همهٔ تنظیماتِ لینک مخزن‌ها، مدل پیش‌فرض، بودجه، permissions و workflowها را بازسازی نمی‌کنند (`src/github/project-files.ts:99–110,585–603`). backup کل سیستم موضوع جداگانه‌ای است؛ «هر زمان فقط با Pull همهٔ DB را می‌توان بازساخت» ادعای درستی نیست.
7. **چند عامل هم‌نوع:** مسیر پیش‌فرض فایل عامل بر اساس type و restore با `byType` است (`src/http/routes/agents.ts:69`، `src/github/project-files.ts:520–537`). حفظ چند عامل هم‌نوع و ایزوله‌بودن IDهای واردشده باید آزمون اختصاصی داشته باشد.

## هشدار وابستگی‌ها

خروجی runtime-only ممیزی npm دو بستهٔ آسیب‌پذیر را گزارش کرد: `@fastify/static` تو‌در‌تو با شدت **high** و `@fastify/swagger-ui` با شدت **moderate**. static مستقیم پروژه از نسخهٔ جدیدتر استفاده می‌کند، اما نسخهٔ وابستهٔ swagger-ui هنوز در درخت نصب وجود دارد.

شناسه‌های advisory: `GHSA-8pvw-jcv7-9cmj` و `GHSA-83w8-p2f5-377r`. پیشنهاد ابزار ارتقای swagger-ui به `6.1.1` است که نسبت به نسخهٔ فعلی **semver-major** محسوب می‌شود؛ هیچ `audit fix --force` یا ارتقای بدون تست انجام نشده است. این خروجی، وجود نسخه‌های مشمول advisory را نشان می‌دهد؛ بهره‌برداری عملی از این دو advisory در این برنامه جداگانه آزمون نشده است. فایل خام: `/home/user/codevia-runtime-audit.json`.

## ترتیب پیشنهادی تکمیل و معیار خروج

1. **پیش از هر انتشار عمومی:** A01–A03؛ سپس approval worker و مسیر اتصال پروژه در A04. تست دو کاربر واقعیِ آزمایشی، هویت جعلی، منابع متعلق به پروژهٔ دیگر و roomهای Socket.io باید دسترسی غیرمجاز را رد کنند. تا آن زمان دسترسی را به محیط مورداعتماد محدود نگه دارید؛ روشن کردن REQUIRE_AUTH به‌تنهایی کافی نیست.
2. **حفظ تصمیم کاربر و سلامت داده:** A05–A12؛ حفظ overrideها، ایندکس/migration عامل‌ها، مدل ارث‌بری‌شده، serialization بدون اتلاف، namespace شناسه‌ها، Pull امن و recovery اجرا. معیار: round-trip کامل و عدم احیای عملیات لغوشده/اثر تکراری.
3. **کامل‌کردن خودِ درخواست اصلی:** A13–A16؛ gate رفع ابهام، context همهٔ مخزن‌های مرتبط، handoff مبتنی بر dependency و verdict مستند QA. معیار: درخواست مسدود هیچ source write نداشته باشد؛ consumer قرارداد producer را بگیرد؛ معیار فاقد شاهد به‌طور خودکار «تکمیل‌شده» محسوب نشود.
4. **یکسان‌کردن قرارداد اجرا:** A17–A18، معنی maxIterations و دامنهٔ نقش‌ها/ابزارها. معیار: action بدون اثر موفق اعلام نشود و رفتار لغو/timeout در ابزار و سرویس خارجی قابل‌ردیابی باشد.
5. **تأیید بیرونی پس از اصلاح:** یک مخزن آزمایشی واقعی، provider واقعی، CI با checkهای اجباری، سناریوهای رابط وب/تلگرام، چندکاربره، چندمخزنی، قطع اتصال و restart. این مرحله در ممیزی حاضر انجام نشده است.

این فهرست برنامهٔ اصلاح است، نه اعلام انجام اصلاح‌ها. بعد از هر تغییر باید تست رفتاری متناظر به regression اضافه و ابزار ممیزی نیز با قرارداد نهایی بازبینی شود؛ صرف سبز کردن شمارنده کافی نیست.

## بازتولید

```bash
# وابستگی‌ها باید نصب باشند؛ مطابق پروژه از Node پشتیبان node:sqlite استفاده کنید.
mkdir -p data/audit
node --import tsx scripts/audit-pipeline.mjs > data/audit/pipeline-audit.json
```

کد خروجی `0`: همهٔ رفتارهای بررسی‌شده برقرارند؛ `1`: شکاف تشخیصی وجود دارد؛ `2`: خودِ یک یا چند probe خطا کرده است. **خروجی فعلی مورد انتظار `1` است، نه یک regression سبز.** خروجی JSON در پوشهٔ نادیده‌گرفته‌شدهٔ `data/audit/` قرار می‌گیرد؛ نیازی به commit دادهٔ runtime نیست.

### جمع‌بندی

پیاده‌سازی نوبت قبل مسیر اصلی و چند حفاظت مهم را اضافه کرده است، اما **«وجود جریان اجرایی» با «اجرای کامل، درست و امن همهٔ نیازمندی‌ها» یکی نیست**. این ممیزی ۱۸ شکاف مشخص را مستند کرده؛ ادعای پوشش صددرصد همهٔ فایل‌ها، همهٔ ورودی‌ها یا آمادگی production ارائه نمی‌کند.

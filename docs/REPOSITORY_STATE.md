# ذخیره و خواندن اطلاعات پروژه از `CodeVia/`

> **وضعیت فعلی پس از بازبینی:** [ممیزی مستقل](REPOSITORY_STATE_AUDIT.md) با وجود موفقیت ۵۴۷ تست، **۸ نقص باز** پیدا کرد. مصرف متن context، مرجعیت تاریخچهٔ پایان‌یافته، حذف پس از کپی/rename، مهاجرت legacy و بعضی خطاهای تنظیم/ذخیره هنوز کامل نیستند. این راهنما را تضمین کامل‌بودن تمام مسیرها ندانید؛ پیش از migration از دیتابیس backup بگیرید.

## قرارداد جدید

**هدف معماری این است که پوشهٔ `CodeVia/` در مخزن متصل هر پروژه مرجع اطلاعات آن باشد، نه صرفاً خروجی اختیاری دیتابیس. مسیرهای پایه پیاده شده‌اند؛ استثناهای ناقص در گزارش بالا ثبت شده‌اند.**

- قبل از استفادهٔ مجدد، تعریف‌های موجود از مخزن خوانده می‌شوند.
- مهارت فقط یک slug نیست: متن دستورالعمل، وابستگی‌ها، نسخه، نقش‌های سازگار و وضعیت فعال/غیرفعال ذخیره می‌شوند.
- ساخت پروژه، اجرای مجدد onboarding و شروع اجرا، ابتدا وضعیت موجود را بازیابی می‌کنند و **فقط فایل‌های واقعاً مفقود** را ایجاد می‌کنند.
- پرامپت، مدل، ابزار، مجوز، محدودیت، مهارت و وضعیت غیرفعالِ ایجنت موجود بازتولید نمی‌شود. تغییر انتخاب‌های پروژه مجوز بازنویسی تعریف‌های موجود نیست.
- خطاهای GitHub، فهرست ناقص و بسیاری از خطاهای ساختاری متوقف می‌شوند؛ اما تبدیل بعضی فیلدهای عددی نامعتبر به پیش‌فرض هنوز نقص باز R08 است.

دیتابیس همچنان برای ایندکس، وضعیت اجرای زنده، صف و اطلاعات محلی اتصال/حساب لازم است. این تغییر، جایگزین پشتیبان‌گیری کامل از دیتابیس یا اصلاح همهٔ مشکلات امنیتی محصول نیست.

## ساختار فایل‌ها

```text
CodeVia/
├── project.md                 # تعریف و تنظیمات غیرمحرمانهٔ پروژه
├── rules.md                   # قوانین پروژه
├── skills.md                  # مهارت‌های متصل به پروژه؛ آرایهٔ خالی هم معتبر است
├── skills/
│   └── <slug>.md              # تعریف کامل هر مهارت
├── agents/
│   └── <role-or-id>.md        # پرامپت‌ها، مدل‌ها، ابزارها، مجوزها و محدودیت‌ها
├── prompts/
│   ├── index.md               # نشانگر انتقال تاریخچه از ایندکس قدیمی
│   └── history/<agent-file>   # نسخه‌های واقعی پرامپت برای مقایسه و بازیابی
├── memory.md                  # حافظهٔ کامل و نسخه‌دار
├── context.md                 # شرح زمینه/معماری؛ نوشتهٔ AI یا کاربر
├── workflows/
│   └── <id>.md                # تعریف کامل گراف و تنظیمات نودها
├── tasks/
│   └── <id>.md                # درخواست، پژوهش، تخصیص مهارت، وابستگی‌ها و نتیجه
├── runs/
│   └── <id>.md                # مراحل قابل مشاهده، نتیجه، مصرف و snapshot مهارت‌ها
├── conversations/
│   └── <id>.md                # پیام‌ها، خلاصه و انتخاب‌های گفت‌وگو
└── runtime/
    └── context.md             # رجیستری تولیدشدهٔ موجودیت‌ها و فایل‌های اجرا
```

ایجنت‌های پیش‌فرض می‌توانند نام فایل مبتنی بر نقش داشته باشند. ایجنت‌های دستی فایل مستقل مبتنی بر شناسه می‌گیرند؛ دو ایجنت هم‌نوع فایل یکدیگر را بازنویسی نمی‌کنند.

`context.md` متعلق به زمینهٔ پروژه است؛ **طبق R01، حفظ آن فعلاً به معنی ورود خودکار متنش به درخواست مدل نیست.** به‌روزرسانی خودکار رجیستری اجرا در `runtime/context.md` انجام می‌شود، نه با پاک کردن یادداشت‌های کاربر.

## چه زمانی از Git خوانده می‌شود؟

1. **ساخت/استفادهٔ دوباره از پروژه:** ابتدا مخزن خوانده می‌شود؛ پوشهٔ موجود دوباره ساخته نمی‌شود.
2. **وب:** نمای پروژه و منابع وابسته، ویرایش‌ها و جست‌وجو، ایندکس را از فایل‌های مخزن تازه می‌کنند. یک GET عادی هزینهٔ تولید AI ایجاد نمی‌کند.
3. **تلگرام:** پس از کنترل دسترسی بات، اطلاعات پروژه‌های مجاز از مخزن تازه می‌شود. لغو کار نباید منتظر دسترس‌پذیر شدن GitHub بماند.
4. **اجرا:** مسیرهای Autonomous، تک‌ایجنت و Workflow از تعریف تازه استفاده می‌کنند. خود runner هم پیش از استفاده از snapshot ایجنتِ فراخوان، دوباره وضعیت را بررسی می‌کند.
5. **حافظه:** ابزارهای خواندن/جست‌وجو/نوشتن حافظه از همین `CodeVia/memory.md` استفاده می‌کنند؛ مسیر جداگانهٔ حافظهٔ محلی برای پروژهٔ متصل وجود ندارد. `force: local` صرفاً یک انتخاب صریح کتابخانه‌ای برای آزمایش/کار بدون اتصال است.

در هر خواندن، HEAD بررسی می‌شود. محتوای یک SHA تغییرناپذیر می‌تواند در حافظهٔ فرایند cache شود؛ تغییر SHA موجب خواندن و اعتبارسنجی snapshot تازه می‌شود. این سازوکار cache زمانیِ «شاید قدیمی» نیست.

## ایجاد محتوای مفقود با AI

مدل فعالِ انتخاب‌شدهٔ پروژه، با محدودیت بودجه، برای نوشتن دستورالعمل‌های اختصاصی ایجنت‌ها، مهارت‌ها، قوانین، شرح گردش‌کار و زمینهٔ اولیه استفاده می‌شود. فناوری‌ای که template آماده ندارد نیز می‌تواند مهارت اختصاصی دریافت کند. وابستگی‌های مفقودِ مهارت‌های فعالِ کشف‌شده در Git، حتی قبل از اتصال صریح، تکمیل می‌شوند. تعریف غیرفعال یا tombstone باعث تولید پیش‌نیاز تازه از طرف خودش نمی‌شود.

- خروجی مدل ساختاریافته اعتبارسنجی می‌شود. پاسخ ناقص/نامعتبر قبل از commit رد می‌شود.
- متن‌های لازم در batchهای کوچک تولید می‌شوند، ولی **یک بودجهٔ مشترک** دارند؛ فایل‌های یک نوبت initialization در پایان، یکجا نوشته می‌شوند.
- مجوز، ابزار، شناسه، مدل اجرایی و حدود بودجه از خروجی آزاد مدل گرفته نمی‌شوند. گراف‌های اولیه از نقش‌های موجود و مرز تأیید انسانی ساخته می‌شوند؛ AI متن و دستورالعمل آن‌ها را تکمیل می‌کند.
- حافظهٔ اولیه، در صورت تولید، شرح پروژه و پرسش‌های باز است؛ نه ادعای اجرای کار، پژوهش بیرونی یا تصمیم تاریخی ساختگی. خروجی AI همچنان نیازمند بازبینی است.
- مصرف مدل در cost ledger ثبت می‌شود. timeout سیگنال لغو را به adapterهای HTTP می‌رساند؛ پاسخ دیرهنگام اجازهٔ commit ندارد. پایان درخواست به معنی تضمین لغو صورتحساب سرویس بیرونی نیست.
- سقف‌های initialization علاوه بر بودجهٔ پروژه: حداکثر ۱۲۸ تعریف در یک نوبت، ۲۴ فراخوانی، ۱۲۰٬۰۰۰ توکن، ۵۰ دلار و ۵ دقیقه. در صورت صفر بودن حد هزینهٔ عمومی، پیش‌فرض initialization پنج دلار است. بودجهٔ کوچک‌تر پروژه مقدم است. مقدار صفرِ بدون محدودیتِ عمومی، این سقف‌های initialization را حذف نمی‌کند.

### نبود مدل واقعی

- **مخزن واقعی + اطلاعات مفقود:** خطای روشن برای پیکربندی مدل/provider؛ تعریف شبیه‌سازی‌شده در مخزن واقعی نوشته نمی‌شود.
- **پوشهٔ کامل موجود:** برای خواندن و بازیابی آن نیازی به فراخوانی مدل نیست.
- **Mock/offline:** scaffold با برچسب صریح `generation: simulation` ساخته می‌شود؛ این خروجی به عنوان تولید واقعی AI معرفی نمی‌شود.

`repositoryState` در manifest، منشأ initialization اولیه را ثبت می‌کند. تعریف‌های موجودِ یک پروژهٔ شبیه‌سازی‌شده با اتصال مدل واقعی خودبه‌خود بازتولید نمی‌شوند. برای تغییرشان صریحاً ویرایش کنید؛ فقط اطلاعات مفقود جدید با مدل نوشته می‌شود.

## ویرایش مهارت‌ها

در صفحهٔ **Skills همان پروژه**، فایل‌های کشف‌شده، وضعیت اتصال و ویرایش تعریف در دسترس‌اند. برای مهارت جدید می‌توان دستورالعمل را خالی گذاشت تا مدل آن را بنویسد؛ متن موجود هرگز خودکار بازنویسی نمی‌شود.

API:

```text
GET    /skills?projectId=<project-id>     تعریف‌های همان پروژه، تازه‌خوانده از Git
POST   /skills                          ایجاد؛ projectId را در body قرار دهید
PATCH  /skills/<skill-id>                ویرایش تعریف
POST   /skills/<skill-id>/disable        غیرفعال‌سازی پایدار
DELETE /skills/<skill-id>                حذف عمدی با tombstone
POST   /projects/<project-id>/skills     اتصال یک تعریف یا کپی صریح template
```

`GET /skills` بدون `projectId`، بازار **templateهای عمومی** است. ارتقا یا غیرفعال کردن template عمومی، نسخهٔ مستقل پروژه را تغییر نمی‌دهد. برای توقف یک مهارت در پروژه، همان تعریف پروژه را غیرفعال کنید. غیرفعال بودن پیش‌نیاز هم مانع قابل‌استفاده بودن مهارت وابسته است.

کشف فایل به معنی افزودن بی‌قیدوشرط آن به همهٔ تسک‌ها نیست. انتخاب مهارت همچنان نقش‌محور و وابسته به وظیفه است؛ متن مهارت مجوز ابزار ایجاد نمی‌کند.

### نمونهٔ فایل مهارت قابل خواندن

```markdown
---
schemaVersion: 2
id: session-contract
slug: session-contract
name: Session contract
description: Keep session APIs compatible with the existing client.
category: project
version: "1.0.0"
tools: []
dependencies: [testing]
compatibleAgentTypes: [backend-developer, qa-test]
metadata: {author: human}
enabled: true
builtIn: false
createdAt: "2026-09-07T00:00:00.000Z"
updatedAt: "2026-09-07T00:00:00.000Z"
---

# Session API
Preserve the existing response shape. Validate expiry and failure cases.
Test compatibility with the current client before proposing a change.
```

نام فایل این نمونه باید `CodeVia/skills/session-contract.md` باشد. شناسه در ایندکس به فضای همان پروژه محدود می‌شود. **در schema 2، بدنهٔ Markdown دستورالعمل مهارت است.**

Front matter تولیدی از مقادیر JSON معتبر در YAML استفاده می‌کند. YAML معمولی و متن چندخطی `|` هم قابل خواندن است؛ کلید تکراری، ساختار خراب و aliasهای YAML پذیرفته نمی‌شوند.

## فیلد مرجع را کجا ویرایش کنیم؟

- `project.md`: شیء `definition` برای تنظیمات پروژه؛ خلاصه‌های نمایشی پایین فایل مرجع مستقل نیستند.
- `rules.md`: آرایهٔ `rules` در front matter؛ فایل سادهٔ Markdown بدون آن نیز به صورت یک متن قانون خوانده می‌شود.
- `skills.md`: آرایهٔ `skills` برای اتصال‌ها؛ `[]` عمداً خالی باقی می‌ماند.
- فایل ایجنت: فیلدهای front matter، از جمله `systemPrompt` و `projectPrompt`.
- فایل مهارت schema 2: metadata در front matter، دستورالعمل در بدنه.
- `memory.md`: آرایهٔ **کامل** `entries` در front matter. بدنه فقط نمایش خوانا است؛ برای ویرایش عادی از Memory وب یا ابزار حافظه استفاده کنید.
- workflow/run/conversation: شیء نام‌گذاری‌شدهٔ همان رکورد در front matter.

`rules.md` و `skills.md` برای قوانین و اتصال‌ها بر نسخهٔ تکرارشدهٔ نمایشی/manifest مقدم‌اند. فایل‌های README داخل پوشه‌های تعریف، تعریف ایجنت یا مهارت تلقی نمی‌شوند.

## تاریخچهٔ پرامپت‌ها هم در Git است

نسخه‌های پرامپت در `CodeVia/prompts/history/` ذخیره و هنگام خواندن از همان‌جا بازیابی می‌شوند؛ فهرست نسخه‌ها، diff و restore به یک جدول محلیِ مستقل وابسته نیستند. فایل‌های تاریخچه، پرامپت جاری را فعال نمی‌کنند: تعریف جاری همچنان `CodeVia/agents/` است.

- تغییر پرامپت و ثبت تاریخچه در یک commit ذخیره می‌شوند؛ خطای commit موفقیت تلقی نمی‌شود.
- نسخه‌های قبلیِ واقعیِ دیتابیس، در اولین migration به فایل‌های مفقود منتقل می‌شوند. `prompts/index.md` پایان این انتقال را مشخص می‌کند؛ پس از آن فقط تاریخچهٔ Git مرجع است.
- اگر هیچ سابقه‌ای موجود نباشد، فقط متن فعلیِ مشاهده‌شده ثبت می‌شود، نه نسخه‌های گذشتهٔ فرضی یا ساخته‌شده توسط AI.
- تاریخچهٔ موجود، خالی یا tombstone هنگام خواندن/onboarding بازتولید نمی‌شود. ویرایش صریح بعدی می‌تواند تاریخچهٔ تازه‌ای شروع کند.
- با کپی مخزن، شناسهٔ نسخه و ایجنت به فضای پروژهٔ جدید محدود می‌شود. جایگزینی یک ایجنت حذف‌شده نیز تاریخچهٔ ایجنت قبلی را پاک نمی‌کند.

## حافظه، حذف و سابقهٔ اجرا

- متن حافظه با تیترهای تو‌در‌تو، کد، Unicode، refs، scope و version حفظ می‌شود؛ truncate چهارکیلوبایتیِ ایندکس حذف شده است.
- کلید مشابه در دو پروژه به یک رکورد مشترک تبدیل نمی‌شود.
- appendهای هم‌زمان در یک store سریال می‌شوند و هر دو متن/ارجاع را حفظ می‌کنند.
- حذف تعریف از API، `deleted: true` در همان فایل می‌گذارد تا onboarding آن را «مفقود» فرض نکند. غیرفعال‌سازی نیز حذف نیست.
- برای پاک کردن قوانین، اتصال مهارت‌ها یا حافظه، آرایهٔ خالی ذخیره کنید؛ فایل‌های اصلی را tombstone نکنید.
- نقص باز: در کپی workflow حذف‌شده یا حذف ایجنت پس از جابه‌جایی فایل، tombstone کافی نیست و تعریف می‌تواند بازتولید شود (R03/R04).
- پاک کردن واقعی فایل تعریف از Git، با حذف API فرق دارد: اگر آن تعریف هنوز لازم باشد، initialization بعدی می‌تواند آن را بسازد.
- Git تاریخچهٔ commitها را نگه می‌دارد؛ حذف یا tombstone، پاک‌سازی اسرار از تاریخچهٔ Git نیست.

**حالت زندهٔ تسک در اختیار executor است.** با این حال، کد فعلی تغییر متن تسک/run پایان‌یافته در Git را هم برای رکورد موجود نادیده می‌گیرد؛ این دامنهٔ بیش از حد، نقص R02 است. Pull، تسک موجودِ لغوشده را از یک فایل قدیمی دوباره فعال نمی‌کند. در بازیابی به دیتابیس خالی، اجرای `running`/`queued`/منتظر تأیید به‌عنوان متوقف‌شده و نیازمند بازبینی ثبت می‌شود، نه اینکه خودکار اجرا یا تأیید شود. این کار، مشکل جداگانهٔ بازیابی leaseهای صف پس از crash را حل نمی‌کند.

## راه‌اندازی دوباره یا کپی مخزن

1. اتصال GitHub و مخزن/شاخهٔ config را در نصب جدید معرفی کنید.
2. پروژه را ایجاد یا گزینهٔ **Load / fill missing** را اجرا کنید.
3. فایل‌های موجود خوانده می‌شوند؛ شناسه‌های پروژه‌ای در کپی مستقل و ارجاع‌های تاریخچه/ایجنت/گردش‌کار بازبسته می‌شوند.
4. مدل‌ها و اطلاعات ورود محلی را جداگانه پیکربندی کنید. شناسهٔ مدل ذخیره‌شده، خودِ API key یا تعریف حساب/provider نیست؛ مدل موجودِ نامعتبر خودکار با provider نامرتبط جایگزین نمی‌شود.

در یک نصب، دو پروژهٔ مستقل نباید هم‌زمان مالک یک مخزن/شاخهٔ config باشند. برای استقلال، مخزن یا شاخهٔ دیگری انتخاب کنید. در تغییر صریح اتصال، پوشهٔ موجود مقصد مقدم است؛ اگر مقصد فاقد وضعیت باشد، اطلاعات فعلی به آن منتقل می‌شود.

## مهاجرت و خطاها

- migration تمام اجزای legacy کامل نیست: ایجنت فقط-DB و workflow سفارشی قدیمی ممکن است از استفادهٔ فعال خارج یا جایگزین شوند (R05/R06).
- فایل‌های قدیمی `CodeVia/` خوانده می‌شوند؛ manifest قدیمی در مسیر migration به schema 2 ارتقا می‌یابد.
- حافظهٔ legacy مبتنی بر تیتر، همراه با نسخهٔ کامل سند خام نگه داشته می‌شود تا نثر خارج از تیترها از دست نرود.
- اگر حافظهٔ جدید وجود نداشته باشد، فایل‌های قدیمی `.ai-engineering/memory/<type>/*.md` به صورت کامل وارد می‌شوند. از این پس حافظه و workflow جدید در `.ai-engineering/` نوشته نمی‌شود.
- `syncProjectState` برای **ذخیرهٔ صریح/مهاجرت** است، نه flush خودکار کل دیتابیس پس از هر اجرا. پایان اجرا فقط فایل‌های runtime متعلق به اجرا را به‌روزرسانی می‌کند.
- `409` یعنی فایل هدف از زمان خواندن تغییر کرده؛ refresh و سپس ویرایش را تکرار کنید. commit قدیمی روی تغییر Git تحمیل نمی‌شود.
- در cancel، شکست Git فعلاً علامت unsynced/retry کافی ندارد (R07)؛ موفقیت لغو محلی را موفقیت ذخیرهٔ Git فرض نکنید.
- خطای خواندن/اعتبارسنجی یا write permission در مسیرهای سخت‌گیرانه، موفقیت ذخیره‌سازی نیست. فایل خراب را در Git اصلاح کنید؛ loader آن را با نسخهٔ قدیمی دیتابیس یا محتوای تازهٔ AI نمی‌پوشاند.
- محدودیت محافظتی: هر فایل ۸ MB، snapshot مجموعاً ۳۲ MB، هر متن حافظه حداکثر ۵۰۰٬۰۰۰ کاراکتر. رسیدن به سقف فهرست ۸٬۰۰۰ مدخل یا سقف ۱٬۰۰۰ مدخل یک پوشه در Contents API واقعی، خطا می‌دهد؛ فهرست ناقص پذیرفته نمی‌شود.
- pushی که با فهرست کامل تغییرات، فقط فایل‌های `CodeVia/` را عوض کرده، QA تازه ایجاد نمی‌کند؛ از حلقهٔ QA → حافظه → push جلوگیری می‌شود. تغییر مختلط کد و وضعیت، صرفاً با پیام commit از QA مستثنا نمی‌شود.

## چه چیزهایی در Git قرار نمی‌گیرد؟

کلید API، توکن، گذرواژه، مقدار رمز‌شدهٔ credential، نشست ورود، مالکیت حساب، اتصال احراز هویت GitHub، lease صف و حساب‌های عمومی پلتفرم جزو دانش پروژه نیستند. فیلدهای credential از serialization حذف می‌شوند و الگوهای شناخته‌شدهٔ کلید خصوصی/توکن در متن نیز پیش از commit رد می‌شوند.

**در متن آزاد هم secret قرار ندهید.** تشخیص خودکار همهٔ رازهای دلخواه تضمین‌شده نیست. secret reference مثل `OPENAI_API_KEY` مجاز است، مقدار آن نه. دسترسی به مخزن باید متناسب با محرمانگی حافظه و گفت‌وگوهای پروژه باشد.

## بررسی فنی

اجرای کنترل‌شدهٔ ۲۰۲۶-۰۹-۰۷: **۵۴۷ تست در ۴۰ فایل** و **۳۳/۳۳ smoke check** عبور کردند؛ ۵۴ تستِ فایل جدید مشخصاً قرارداد repository-first را پوشش می‌دهند. Typecheck و build نیز موفق بودند.

آزمون‌های `src/tests/repository-state.test.ts` شامل ساخت AI با provider ساختگی، missing-only، عدم بازتولید، دست‌کاری خارجی فایل، تضاد concurrent reader، حافظهٔ بلند، دیتابیس واقعاً خالی، کپی پروژه، APIهای ویرایش/حذف، timeout/بودجه، schema خراب و جلوگیری از حلقهٔ webhook هستند.

```bash
npm run typecheck
npm test
npm run build
npm run smoke
node --check public/app.js
```

این‌ها آزمون Mock/ساختگی‌اند؛ معادل اتصال واقعی به مدل پولی یا GitHub نیستند. [گزارش ممیزی قبلی](PIPELINE_AUDIT.md) یک snapshot تاریخی قبل از این تغییر است. کنترل دسترسی، realtime، QA و بازیابی صف همچنان به بررسی و اصلاح جداگانه نیاز دارند؛ این قابلیت، اعلام آمادگی برای استقرار عمومی/چندکاربرهٔ حساس نیست.
